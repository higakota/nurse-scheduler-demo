# 課題・要件・確認状況

## 開発の背景

開発のきっかけは、複雑な勤務条件を満たす表を毎月作ることが大変で、時間がかかっていたことです。使用者は、医師の人数に応じた看護師の配置、検査室の人数と職種、希望休・有給、会議、公休日数などを照合し、変更のたびに人数や連勤を見直す必要がありました。入力、自動作成、変更確認、印刷を一つのアプリで扱い、変更後も保存した勤務表を追えるようにすることを目指しました。

使用者への聞き取りだけで仕様を固定せず、実際に操作してもらった感想と、不具合の指摘を受けて見直しています。

聞き取りでは、医師1人につき診察室の看護師1人が必要なこと、検査室は検査技師2人でも担当できること、会議中の人を診療人数に数えないことなどを確認しました。[聞き取った内容と勤務表の作成条件](scheduling-rules.md)に、配置例とあわせてまとめています。

## 担当範囲と生成AIの利用

| 担当 | 内容 |
|---|---|
| 本人 | 使用者への聞き取り、仕様の判断、操作確認、不具合の指摘 |
| 生成AI | コードの実装、調査、テストコード作成、文書整備の支援 |
| 使用者 | 業務上の条件の説明、画面を使った感想、必要な修正の相談 |

すべてのコードを本人が手書きした開発ではありません。要望をそのまま機能名として並べるだけでなく、どの場面で困るか、何を固定して何を変えてよいか、画面上でどう確認するかを判断し、AIを用いた実装へ反映しています。コードを理解・説明するための入口は [実装を追うガイド](explain-the-code.md) にまとめています。

## 変更をどう判断したか

### 業務ルールの確認から修正した例

検査室に2人必要なとき、検査技師と看護師の組み合わせだけを想定すると、検査技師が2人いても看護師不足になります。使用者との確認を通じて職種の扱いを修正し、配置の探索・結果の検証・不足表示をそろえました。[変更とテスト](case-studies.md#2-検査室の人数と職種を正しく数える)

### 操作確認から設計を変えた例

応援を1行へまとめる案を画面にも適用しましたが、狭い日付列では氏名が読みにくくなりました。使用者の反応を受け、画面では個人別へ戻し、印刷では集約を残しました。[試行と見直し](case-studies.md#5-見やすさの改善案を利用者の反応で見直す)

### 不具合を保存状態の問題として見直した例

「画面移動後に古い勤務表が開く」という指摘に対して、リンクの表示だけでなく、元の表の種類・版・入力条件を照合する処理へ変更しました。異なる表を入れた一時DBで、表示対象と保存前後の状態を確認しています。[変更と回帰テスト](case-studies.md#1-編集後に古い勤務表が開く)

## 現在の確認状況

| 対象 | 状態 |
|---|---|
| 公開サンプルの入力・作成・変更・印刷 | 仮名と一時DBで自動テスト。操作動画では保存とヘルプ反映まで確認 |
| 公開体験版 | 架空データのみ。利用者別の一時保存を分離し、Linuxで起動確認 |
| Windowsの配布・更新・復帰 | 同じWindows PCの別フォルダで実行ファイルを使い、登録データの保持を確認 |
| 使用者の別PCへの導入 | 初回の実機確認は未実施 |
| 業務時間・作業負担への効果 | 未測定。削減率や導入人数を成果として掲載しない |
| 完成した勤務表の業務上の判断 | 使用者による人数・希望・勤務条件の最終確認が必要 |

## 残っている課題

- 使用者の別PCで、インストールからバックアップの復元、印刷までを確認する。
- 操作を説明しなくても、入力から印刷まで進められるか確認する。
- 実際の作業時間と修正回数を記録し、改善の効果を確かめる。
- 実務の公開サービスにする場合の認証・権限管理・監視は別途設計する。
