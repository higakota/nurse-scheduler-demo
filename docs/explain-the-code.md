# コードを追って説明する3つの改善

実装とテストを使って、変更の理由を説明するためのガイドです。本人の担当範囲や経験を代筆したものではありません。

## 1. 古い勤務表への遷移と上書きを防ぐ

**短く説明するなら**：自動作成した表と編集中の表が別にあるため、「どの表を見ているか」を種類・版・入力条件で照合するようにした。

**困っていたこと**：編集後の画面遷移で古い表が開く。作成結果を見るだけのつもりで、編集済みの表が変わると困る。

**処理を追う順番**

1. [roster_navigation.py](../roster_navigation.py) で表の時刻や更新候補を扱う。
2. [schedule.py](../schedule.py) の `read_snapshot` で現在の条件と指紋を読む。
3. [manual_schedule.py](../manual_schedule.py) で元の表の確認・変更差分・保存を扱う。
4. [test_roster_navigation.py](../tests/test_roster_navigation.py) の `test_creation_step_five_opens_exact_result_as_read_only_review` を読む。

**確認していること**：確認画面を開いてもDBを変更しない。リンク先の表が間に更新された場合、代わりの表を黙って開かない。

**聞かれたときに区別すること**：更新時刻で新しいものを選ぶだけの処理と、利用者が指定した表を開く処理は目的が異なる。

## 2. 合計人数と職種別の条件を分ける

**短く説明するなら**：検査室に2人必要な場合、検査技師＋看護師だけでなく検査技師2人も扱い、配置の探索・検証・不足表示を揃えた。

**困っていたこと**：人数は足りていても、職種の想定が狭いと看護師不足が誤って残り、応援の依頼先を判断しにくい。

**処理を追う順番**

1. [scheduler_engine.py](../scheduler_engine.py) の `prepare` で勤務条件を整える。
2. 同じファイルの `verify` で作成結果を独立して確認する。
3. [help_limits.py](../help_limits.py) で応援の職種を扱う。
4. [test_help_role_preference.py](../tests/test_help_role_preference.py) の `test_mixed_pair_is_preferred_and_two_technicians_count_as_two_c_staff` を読む。

**確認していること**：検査技師2人が検査室2人分を満たし、不足表示も一致する。必要な条件では看護師2人の応援も拒否しない。

**聞かれたときに区別すること**：必須条件と、できれば看護師の応援を分散したいという優先方針は別に扱う。最適解が常に見つかるとは保証していない。

## 3. 会議参加者の変更を一括保存する

**短く説明するなら**：複数人・複数日の変更をまとめて確認し、古い画面や不正な入力なら一部だけ保存しないようにした。

**困っていたこと**：1人ずつ保存すると再表示でカレンダーの位置が戻り、連続した入力を続けにくい。

**処理を追う順番**

1. [static/monthly.js](../static/monthly.js) で画面の変更を保持する。
2. [meeting_attendance.py](../meeting_attendance.py) で変更対象・会議・参加者・版を検証する。
3. [tests/test_meeting_attendance.py](../tests/test_meeting_attendance.py) の `MeetingBatchTest` を読む。

**確認していること**：複数人の追加と削除を同時反映できる。不正なセルが1つあれば全件を保存しない。別画面で更新された後の古い一括保存も拒否する。

**聞かれたときに区別すること**：入力をまとめるUIの改善と、まとめた変更を安全に保存する処理の両方が必要。

## 説明の練習

各事例について、コードを見ながら「課題 → 守る条件 → 修正した処理 → テスト → 残る制限」を1分程度で説明してみる。分からない処理は、担当したと言い切らず確認する。自分が判断・確認した範囲と、生成AIを使った実装・調査の範囲は、事実に合わせて整理する。
